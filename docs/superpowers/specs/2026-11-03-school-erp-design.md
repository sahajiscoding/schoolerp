# Pacific World School ERP — v1 Design

- **Date:** 2026-11-03
- **Status:** Approved by owner, pending written-spec review
- **Owner:** Sahaj Chugh
- **School:** Pacific World School
- **Reference UI:** `https://pws.schoolforschools.ai/dashboard` (student dashboard) and supplied mobile screenshots

## 1. Problem

Pacific World School's previous ERP was unreliable. The school has authorized a replacement. The first release must cover the daily academic loop — teachers distributing and collecting work, and communicating with students — with an administrative console the school can actually operate.

The product is a **single-school internal system**, not a multi-tenant SaaS. Adding a second school later is a deliberate migration, not a configuration flag.

## 2. Goals

1. An admin can create the roster: people, classes, sections, subjects, teaching assignments, enrollments.
2. A teacher can distribute an assignment to one or more sections and/or individually selected students, and see who submitted.
3. A student sees only work targeted at them and can submit text and a file.
4. A teacher can hold a private threaded conversation with any student they teach; admins can read every thread for safeguarding.
5. An admin can publish a one-way notice to the whole school, a role, selected sections, or selected people, with read counts.
6. Push notifications arrive for new assignments, messages, and notices.
7. No third-party secret is readable from an installed app.
8. Any agent can determine project state from one file.

## 3. Non-goals for v1

- Fees, payments, receipts
- Attendance
- Report cards, marks, rubrics, gradebook
- Library, gallery, events, course progress
- Parent accounts and parent-facing views
- Student-to-student messaging
- Multi-school tenancy
- Offline write queue
- Web version of the student/teacher experience
- Public self-signup

The data model leaves room for guardians and academic records, but no speculative tables are created.

## 4. Users and permissions

| Action | Admin | Teacher | Student |
|---|---|---|---|
| Create users, reset passwords, deactivate | yes | no | no |
| Manage classes, sections, subjects | yes | no | no |
| Assign teacher to section + subject | yes | no | no |
| Enroll students | yes | no | no |
| Create assignment | no | own sections only | no |
| View assignment | all | authored | targeted only |
| Submit assignment | no | no | own, if targeted |
| Review submission | read-only | authored | no |
| Start thread | no | students in own sections | no |
| Reply in thread | no (read-only) | own threads | own thread |
| Publish broadcast notice | yes | no | no |
| Read any thread (audited) | yes | no | no |
| View audit log | yes | no | no |

Teacher reach is always derived from `teaching_assignments` inside RLS. It is never trusted from the client.

## 5. Architecture

```
Expo app (teacher + student) ─┐
                              ├─► Supabase
React/Tailwind admin (Vercel) ┘    ├─ Postgres + Row Level Security
                                   ├─ Auth
                                   ├─ Storage (private buckets)
                                   ├─ Realtime (thread updates)
                                   └─ Edge Functions (privileged only)
                                        ├─ admin-users
                                        └─ notify
```

### Authorization: RLS-first

Every table has RLS enabled with default-deny. Clients query Postgres directly under the user's JWT. Only operations that cannot be expressed as a SQL policy go through Edge Functions holding the service role: creating auth users, resetting passwords, bulk import, and push fan-out.

**Alternatives considered**

- *Single backend API layer:* safest to reason about, but requires rebuilding querying, pagination, and realtime; discards Supabase's core value.
- *All logic in Postgres RPC functions:* strong auditability, painful for list screens and client caching.
- *RLS-first with narrow Edge Functions:* chosen. Fast to build, but RLS becomes the only wall, so the RLS test matrix is mandatory.

### Repository layout

```
schoolerp/
  apps/
    mobile/            Expo + expo-router + NativeWind
    admin/             React + Vite + Tailwind + TanStack Query
  packages/
    shared/            types, Zod schemas, targeting logic, Supabase client factory
  supabase/
    migrations/
    functions/
    seed.sql
    tests/             pgTAP RLS tests
  docs/
    superpowers/specs/
  AGENTS.md
  PROJECT_STATUS.md
```

Monorepo with npm workspaces. One repository keeps shared types, migrations, and the status document in lockstep. A second repository would drift.

## 6. Data model

All tables are in `public`, use `uuid` primary keys generated by `gen_random_uuid()`, carry `created_at`, and reference `auth.users(id)` through `profiles`.

| Table | Columns and constraints |
|---|---|
| `profiles` | `id` pk = auth user, `role` enum(`admin`,`teacher`,`student`), `full_name`, `login_id` unique, `must_change_password` bool default true, `is_active` bool default true, `avatar_path` nullable, `created_at` |
| `classes` | `name` (e.g. "Grade 8"), `sort_order` int |
| `sections` | `class_id` fk, `name` (e.g. "A"), `academic_year` text, unique(`class_id`,`name`,`academic_year`) |
| `subjects` | `name`, `code` unique |
| `teaching_assignments` | `teacher_id` fk profiles, `section_id` fk, `subject_id` fk, unique triple. A teacher may hold many rows. |
| `enrollments` | `student_id` fk profiles, `section_id` fk, `roll_no` text, `academic_year`, unique(`student_id`,`academic_year`), unique(`section_id`,`roll_no`,`academic_year`) |
| `assignments` | `teacher_id`, `title`, `instructions`, `due_at` timestamptz nullable, `attachment_path` nullable, `published_at`, `created_at` |
| `assignment_sections` | `assignment_id`, `section_id`, pk both |
| `assignment_students` | `assignment_id`, `student_id`, pk both — for individually targeted students |
| `submissions` | `assignment_id`, `student_id`, `body` nullable, `file_path` nullable, `submitted_at`, `status` enum(`submitted`,`reviewed`), `reviewed_at` nullable, unique(`assignment_id`,`student_id`), check body or file present |
| `threads` | `id`, `teacher_id`, `student_id`, `subject`, `campaign_id` uuid not null default `gen_random_uuid()`, `last_message_at`, unique(`teacher_id`,`student_id`,`campaign_id`). Every thread has a campaign id so the unique constraint always applies; multi-recipient messages share one id. |
| `messages` | `thread_id`, `sender_id`, `body` non-empty, `created_at` |
| `notices` | `id`, `created_by` (admin), `title`, `body`, `published_at` |
| `notice_recipients` | `notice_id`, `user_id`, `read_at` nullable, pk both — materialized at publish |
| `push_tokens` | `user_id`, `expo_token`, `platform` enum(`ios`,`android`), unique token |
| `notification_jobs` | `id`, `kind`, `entity_id`, `recipient_id`, `idempotency_key` unique, `status` enum(`pending`,`sent`,`failed`), `attempts`, `last_error` |
| `audit_log` | `id`, `actor_id`, `action`, `entity_type`, `entity_id`, `meta` jsonb, `created_at` |

### Derived views

- `assignment_recipients` — view that unions section enrolments with individually targeted students, filtered to active users. Used for visibility and the teacher's submission roster.
- `unread_counts` — view per user for notices and threads.

All views are created with `security_invoker = true` (Postgres 15+) so they run under the caller's RLS rather than the view owner's. A view without this setting silently bypasses RLS and is treated as a security defect.

## 7. Targeting rules

These rules are implemented as pure functions in `packages/shared/src/targeting.ts`, mirrored by SQL helper functions used in RLS, and unit-tested against each other.

1. An assignment's recipients are `union(enrolled students of assignment_sections, assignment_students)`, deduplicated by student id, limited to active users.
2. A teacher may add a section target only if a `teaching_assignments` row exists for that teacher and section.
3. A teacher may add an individual student only if that student is enrolled in a section the teacher teaches.
4. A message composed to N students creates N private threads sharing one `campaign_id`. Students never see other recipients or other replies. The teacher sees the grouped campaign in their inbox.
5. A teacher may reply only in threads where they are `teacher_id`. A student may reply only in threads where they are `student_id`.
6. Notice audience types: `school`, `role`, `section`, `user`. The audience is expanded into `notice_recipients` at publish time inside a single transaction.
7. Targeting is rejected, not silently filtered. An unauthorized target returns an error so a bug cannot become a quiet privacy leak.

## 8. Security model

### Public by design (safe in an APK/IPA)

- `EXPO_PUBLIC_SUPABASE_URL`
- `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (preferred) or `EXPO_PUBLIC_SUPABASE_ANON_KEY` (legacy)
- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY` (preferred) or `VITE_SUPABASE_ANON_KEY` (legacy)

The publishable/anon key is not a credential. It grants the `anon` Postgres role and is only safe because RLS denies by default.

### Server-side only

- `SUPABASE_SERVICE_ROLE_KEY` — legacy JWT that bypasses RLS; total database compromise if leaked
- `SUPABASE_SECRET_KEY` — new-format secret that bypasses RLS; same severity
- `SUPABASE_JWT_SECRET` — signs access tokens; leakage permits forged tokens for any role
- `POSTGRES_URL`, `POSTGRES_PRISMA_URL`, `POSTGRES_URL_NON_POOLING`, `POSTGRES_USER`, `POSTGRES_HOST`, `POSTGRES_PASSWORD`, `POSTGRES_DATABASE` — direct database credentials
- `EXPO_ACCESS_TOKEN` — push sending
- Future: payment, SMS, email, AI provider keys

These exist only in Supabase Edge Function secrets and local `supabase/.env.local` (gitignored). They are never referenced in `apps/`, never prefixed `EXPO_PUBLIC_`/`VITE_`, and never committed.

The Vercel Supabase integration injects an additional Next.js-specific set (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`). Vite and Expo ignore these names, so they must not be used in this repository. Full variable-by-variable classification and rotation procedure: `docs/security/environment-variables.md`.

### Edge Functions

**`admin-users`** — service-role operations: create user, deactivate, reset password, CSV import.

1. Reject missing/invalid JWT.
2. Load the caller's `profiles` row; require `role = 'admin'` and `is_active`.
3. Validate body with a Zod schema.
4. Perform the operation with the service-role client.
5. Write an `audit_log` row.
6. Return only non-sensitive fields.

**`notify`** — push fan-out.

1. Reject missing/invalid JWT.
2. Verify the caller is the author of the referenced assignment/thread, or an admin for notices.
3. Expand recipients server-side; never accept a recipient list from the client.
4. Insert `notification_jobs` with an idempotency key; send through Expo; update status.
5. On failure, record `last_error` and let a retry read pending jobs.

Both functions are treated as public endpoints: anyone with the anon key can invoke them.

### RLS

- Default deny on every table.
- Helper functions: `current_role()`, `is_admin()`, `teaches_section(uuid)`, `is_enrolled(uuid)`, `can_view_thread(uuid)`, `is_thread_participant(uuid)`.
- Students read their own profile, assignments targeted at them, their own submissions, their own threads and messages, notices addressed to them, and their own push tokens.
- Teachers read profiles of students in their sections, their authored assignments, submissions for those assignments, their own threads, and section rosters.
- Admins read everything, but **never write** to assignments, submissions, threads, or messages.
- `audit_log` is insert-only for service role, select for admins.
- Deactivated users resolve to no role and fail every policy.

### Storage

- Buckets: `assignment-attachments`, `submission-files`, `avatars` — all private.
- Object path convention: `<bucket>/<owner_uuid>/<uuid>-<filename>`.
- Insert policy requires the first path segment to equal `auth.uid()`.
- Read access through short-lived signed URLs generated after an RLS-authorized row check; never public URLs.
- Upload limits: 10 MB per file; MIME allowlist: PDF, JPEG, PNG, DOCX.

### Application hardening

- Sessions in `expo-secure-store` on mobile, not AsyncStorage.
- Admin SPA: strict CSP, no `dangerouslySetInnerHTML`, pinned dependencies.
- No Aadhaar, address, or phone number collected in v1.
- Account deletion request screen for store compliance; request is queued for admin action.
- Login identifiers: students use admission number, staff use staff ID, mapped to a deterministic internal email for Supabase Auth. Passwords are set by admin and must be changed on first login.
- No public signup route exists.
- CI check fails on `EXPO_PUBLIC_.*(SECRET|SERVICE|PRIVATE)` and on secret-like strings in `apps/`.

### Safeguarding

Every admin read of a thread writes an `audit_log` row. Threads are retained for the academic year and archived, not silently deleted. There is no student-to-student channel. Admin cannot post inside a teacher-student thread.

## 10. Visual direction

Derived from the school's existing identity: deep olive header, terracotta accents, sand background, near-black ink, muted grey secondary text. Mobile uses cream surfaces with rounded cards and a warm accent; admin uses the same tokens with denser spacing. Inter for UI. Logo and crest supplied by the school; no invented branding.

Tokens live in `packages/shared/src/theme.ts` and are consumed by Tailwind config (admin) and NativeWind config (mobile) so the two apps cannot drift.

## 11. Notifications

- Expo Push Service. Device tokens registered to `push_tokens` on login and refreshed on change.
- Assignment publish, new thread message, and notice publish create `notification_jobs`.
- The client calls `notify` after a successful insert; the function verifies authorship and expands recipients server-side.
- Push payloads carry ids only, never message bodies or student names, so lock-screen previews do not leak content.
- Tapping a notification deep-links to the relevant screen.
- A user can mute categories; muting does not affect in-app records.

## 12. Offline behaviour

TanStack Query caches reads. Writes require connectivity in v1; the UI shows an explicit offline banner and disables submit. No background sync queue. This is a deliberate scope cut, revisited after launch.

## 13. Progress tracking and the agent contract

- `PROJECT_STATUS.md` is the single source of truth for state: current milestone, done, in progress, next, deferred, known issues, decisions, secrets manifest, and open questions. Entries link to files.
- `AGENTS.md` is loaded automatically by OpenCode and Claude Code. It requires every agent to read the status file before work and update it before finishing, and forbids client-side secrets.
- CI warns when `apps/**` or `supabase/**` changed without a `PROJECT_STATUS.md` change. Warning, not failure.

## 14. Testing

- **RLS matrix (pgTAP):** actor × table × row coverage. At minimum: student cannot read another student's submission or thread; teacher cannot read a section they do not teach; teacher cannot target a foreign section; admin can read everything but cannot insert into `messages`; deactivated user reads nothing; anon reads nothing.
- **Targeting unit tests:** dedupe, permission filtering, rejection of unauthorized targets, equality with SQL helper behaviour.
- **Edge Function tests (Deno):** unauthenticated, authenticated-but-wrong-role, correct role, malformed body.
- **Mobile smoke (Maestro):** login → assignment → submit → reply.
- RLS tests run on every migration. A migration without tests is incomplete.
